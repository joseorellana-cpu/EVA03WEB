# F-15 · Autoevaluación contra el test de seguridad (F01–F14)

Este documento pretende ser **honesto**: marca lo cumplido por el frontend,
lo que depende del backend y lo que **sigue vigente** como limitación.

| ID | Control | ¿Cómo se cumple en el frontend? | Archivo(s) | Limitación que sigue vigente |
|---|---|---|---|---|
| F01 | Autenticación | **NO cumplido (por diseño del lab):** se usa identidad simulada `X-Usuario`. | `src/stores/usuarioStore.js`, `src/App.vue` (banner visible) | El usuario es falsificable; no hay firmas, tokens ni sesiones. En producción exige OAuth2/OIDC. El backend graba el header tal cual en auditoría. |
| F02 | Render seguro | **Cumplido.** Prohibido `v-html`, `innerHTML`, `eval`; todo dato se muestra con interpolación `{{ }}`; el linter bloquea `vue/no-v-html`. | `eslint.config.js`, `src/components/*`, `src/views/**` + test anti-XSS | Ninguna, mientras se respete la regla. |
| F03 | Almacenamiento de datos sensibles | **Cumplido en el alcance del lab.** Sin tokens ni datos sensibles en `localStorage`. El usuario simulado vive en memoria (Pinia) y como respaldo en `sessionStorage` (pestaña). | `src/stores/usuarioStore.js` | Si alguien introduce datos sensibles en el futuro, seguirán en `sessionStorage`. La regla es: ningún secreto ni dato privado. |
| F04 | Autorización en cliente (ocultar acciones según estado) | **Cumplido como UX,** no como barrera. La UI oculta acciones no válidas (editar ANULADA, confirmar si no es REGISTRADA, etc.), pero siempre redirige el guardado al backend. | `src/views/compras/*.vue`, `src/views/proveedores/ProveedorListView.vue` | La ocultación NO evita que alguien fuerce la petición: el backend sí valida y responde 403/409. |
| F05 | Control de acceso a la API (backend) | **No cumple (depende del backend):** los botones dependen del estado, pero el backend decide. | — | Implementar en backend: autorización por recurso + rol; CSRF por tokens; reglas BFLA por endpoint. |
| F06 | Cabeceras de seguridad / CSP | **Cumplido en despliegue ejemplo:** `nginx.conf` con CSP estricta (`default-src 'self'`; `script-src 'self'`; sin `unsafe-inline` ni `unsafe-eval`; `connect-src 'self'`; `frame-ancestors 'none'`; `base-uri 'self'`; `form-action 'self'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options: DENY` y HSTS sólo con HTTPS. | `frontend/nginx.conf` | En dev (Vite) las cabeceras no se aplican; en prod se entregan vía nginx. |
| F07 | Secretos y gestión de la configuración | **Cumplido.** Ningún secreto en código ni en `.env` versionados; `.env.example` con sólo `VITE_API_BASE_URL` (vacía en prod) y `VITE_API_PROXY_TARGET` (localhost dev). | `.env.example`, `.gitignore`, `vite.config.js` | Cuando se introduzca un backend real con credenciales externas, usar gestor de secretos (Vault/KMS) y rotación. |
| F08 | Dependencias seguras | **Cumplido para producción:** `npm audit --omit=dev` = **0 vulnerabilidades**; `package-lock.json` versionado; sin SNAPSHOT/RC; versiones actuales (Vue 3.5.x, Vite 8, etc.). | `frontend/package.json`, `frontend/package-lock.json` | `npm audit` reporta **11 moderadas** en devDeps (eslint, vite-plugin-vue-devtools, jsdom) — no afectan al bundle; se documentan en el README. Se actualizan periódicamente. |
| F09 | Validación en cliente vs servidor | **Cumplido como espejo (hints).** El cliente valida formato/longitud para UX; el backend es la autoridad y sus errores 400 se muestran tal cual. | `src/utils/validators.js`, `src/utils/money.js`, formularios | El cliente **nunca sustituye** la validación server-side; se asume que el backend limita el payload y pone cabeceras de seguridad (nginx). |
| F10 | Dinero e integridad numérica | **Cumplido.** Aritmética en **centavos enteros** (`money.js`); validación por regex; `Number.isSafeInteger`; nunca flotantes para sumar precios. | `src/utils/money.js` (+ pruebas) | El cálculo final lo hace el backend; el frontend muestra un total **estimado** con igual semántica ("est."), no es autoridad. |
| F11 | Doble envío / idempotencia | **Cumplido como UX (no como protección):** el guardián deshabilita el botón y evita la segunda petición. Se documenta que la idempotencia real es **server-side**. | `src/composables/useAccionUnica.js`, `src/components/BotonAccion.vue` | El guardián no evita recargar la página ni otras pestañas; el servidor debe aplicar idempotencia (clave de solicitud, deduplicación o reglas de negocio). |
| F12 | Manejo de errores | **Cumplido.** Módulo único de normalización; `ErrorApi` con `status/message/details[]`; 503 o fallo de red → mensaje genérico en español; sin `console.log` de respuestas en producción; nunca trazas ni objetos crudos. | `src/api/apiClient.js`, `src/components/AlertaError.vue`, `src/components/FormErroresServidor.vue` | El detalle táctico de las trazas corresponde al backend (logs server-side). |
| F13 | Navegación segura | **Cumplido.** Enlaces externos con `rel="noopener noreferrer"`; sin redirecciones a URLs de parámetros; `:id` validado como entero positivo antes de llamar a la API; ruta comodín 404. | `src/router/index.js`, vistas | — |
| F14 | Transporte y red | **Cumplido en dev/prod ejemplo:** todas las peticiones con timeout (10 s, `AbortController`), sólo al origen configurado, `Content-Type: application/json`, `credentials: 'same-origin'`. | `src/api/apiClient.js`; `nginx.conf` (proxy mismo origen) | La TLS depende de la infraestructura (nginx + certificado); en dev es HTTP local, sin datos reales. |
